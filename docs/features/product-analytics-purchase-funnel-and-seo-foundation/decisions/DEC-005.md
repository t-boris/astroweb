## Context

DEC-001 requires the Stripe webhook to always send purchase and subscription events to GA4, anonymised when the checkout metadata does not record analytics consent = granted. External fact (to be verified against current GA4 docs): for web data streams, the GA4 Measurement Protocol requires client_id in every payload and silently drops payloads without it. As written, the REQ-002 criterion 'no client_id' would make every anonymous purchase disappear from GA4 without any error (F-001).

## Alternatives

1. Random single-use client_id per transaction (UUID v4), never stored or reused
2. Do not send events to GA4 without consent; anonymous revenue is visible only in the admin Business tab (Firestore), revising DEC-001

## Decision

When analytics consent = granted is absent from the checkout metadata, the webhook sends the GA4 event with a pseudo client_id derived deterministically from the Stripe session id: a one-way hash (e.g. SHA-256, truncated and formatted as a GA-style client_id). No user_id and no other user identifier are sent. Webhook retries for the same session produce the same client_id and the same transaction_id. With consent granted, the real GA client_id from the metadata is used, as before.

## Reason

GA4 accepts the hit, so GA4 revenue stays complete, as DEC-001 intends. A deterministic ID keeps webhook retries consistent without storing any state: the same session always maps to the same client_id. The ID is derived only from the payment transaction identifier, not from the user's device or account.

## Consequences

REQ-002 criterion changes to: 'Without consent, client_id is a one-way hash of the Stripe session id; no user_id or other user identifier is sent.' DEC-001 is refined accordingly. The /privacy page (REQ-004) and the GA4 legal reasoning checklist must state that a pseudonymous identifier derived from the transaction id is sent. This is a weaker legal position than a random ID because the ID is linkable to the payment record in Stripe/Firestore, so the legal reasoning must cover it. Each anonymous purchase appears in GA4 as a separate user with no channel attribution, which slightly inflates user counts. Subscription renewal and cancel events have no checkout session (F-003), so the derivation source for them (e.g. the Stripe invoice or subscription event id) still has to be defined. The GA4 requirement for client_id must be verified against current documentation.
