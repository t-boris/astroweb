## Context

REQ-002 requires Chiron. The engine runs Swiss Ephemeris in Moshier mode with an empty ephemeris path, and calc_ut for Chiron fails there with "SwissEph file 'seas_18.se1' not found". With the asteroid file seas_18.se1 present, Chiron reproduces both dated Astro-Seek screenshots to the arcminute (8 deg 54 min Capricorn for 30 Mar 2002 and 0 deg 15 min Sagittarius for 25 Sep 1999). The owner was asked and chose to bundle the file (answer recorded in this conversation, 2026-11-21). The file is 240041 bytes, SHA-256 911a60ed2d706049dab426c03ebc58978fbef20ffd22f9ad957daa2a721e7d89, from the official Astrodienst repository (github.com/aloistr/swisseph, ephe/seas_18.se1), header: based on JPL DE441, covers 1800-2400 AD.

## Alternatives

1. Leave Chiron out: no new data file, but REQ-002 would stay unmet for Chiron and the gap would be recorded in the specification.

## Decision

Commit seas_18.se1 under functions/ephe/ and point the Swiss Ephemeris path at it. Only Chiron reads it. The ten standard bodies, nodes, Lilith and houses keep their Moshier calculation. A birth date outside the file's range, or an unreadable file, yields no Chiron for that chart rather than an error.

## Reason

It is the only way to deliver Chiron at reference precision without changing the engine for any other point, and it adds no npm dependency.

## Consequences

The deployed functions source carries a 240 KB binary asset; its SHA-256 is recorded in the verification evidence. The open licensing question for Swiss Ephemeris in docs/research/2026-11-21-natal-chart-frameworks.md (node 32) now also covers this data file and stays with the owner. Tests cover Chiron inside the range and the no-Chiron fallback outside it.
