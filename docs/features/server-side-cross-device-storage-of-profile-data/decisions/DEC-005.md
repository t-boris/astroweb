## Context

The last entry of discussion.md asked where to store deep texts, compatibility readings and the Oracle history, with two options, and the decision was not recorded. overview.md calls the layout an implementation detail and plan.md I-3 says 'storage linked to each profile'. The existing code already uses oracleHistory/{profileId}/items. Answered by the owner on 2026-10-12.

## Alternatives

1. Subcollections under profiles/{id}/... (a mixed layout, because oracleHistory stays where it is, and Firestore does not delete subcollections with the parent document either)

## Decision

Add two top-level collections next to the existing oracleHistory: deepTexts/{profileId}/items/{blockKeyHash} and compatibilityReadings/{profileId}/items/{contentHash}. oracleHistory/{profileId}/items stays as it is. All three are reachable only through callable Functions (firestore.rules keeps denying all client access). Document ids of deep texts and readings are content-derived, so a repeated write overwrites or skips instead of duplicating.

## Reason

One layout for all three kinds, the same as the one forgetDossier already cleans, and ownership is always checked through the profile in a callable.

## Consequences

Deleting a profile must delete the three collections explicitly (DEC-006). The compatibility-readings limit 'last 20' is dropped, because readings are paid. A single read callable returns all three kinds for an owner.
