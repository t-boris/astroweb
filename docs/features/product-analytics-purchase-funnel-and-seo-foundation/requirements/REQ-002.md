## Statement

The Stripe webhook and direct-order fulfillment send purchase and subscription start/renewal/cancel events to GA4 via the Measurement Protocol for every successful live event. Completed direct-service orders are reported in the same `purchase` conversion funnel whether paid entirely in USD, in a mix of USD and stars, or entirely in stars (simpler-horoscope-discovery-and-purchasing DEC-008): `value` records the actual USD amount charged (USD 0 for fully star-funded orders), and fully star-funded orders are recorded after order completion and deduplicated by their unique order ID without requiring a Stripe session. Checkout metadata (and the direct order document for star-funded orders) carries the GA client_id and the analytics consent state at checkout time. For the astrologer subscription, subscribeAstrologer also writes the GA client_id, the Firebase Auth uid (if signed in) and the analytics consent state into subscription_data.metadata. The webhook reads these values from the Stripe subscription metadata for renewal and cancel events. The consent state recorded at subscription checkout applies to all events of that subscription. Later withdrawal of consent does not update the subscription metadata. When the relevant metadata records analytics consent = granted, the event uses the stored real GA client_id, plus user_id (= Firebase Auth uid) if the user was signed in. When consent = granted is not in that metadata, the event is sent anonymously. It carries no user_id and no other user identifier. Its client_id is a pseudo client_id: a one-way hash (e.g. SHA-256, truncated and formatted as a GA-style client_id) derived deterministically from a Stripe identifier (checkout session id, invoice id, or subscription+event id) or from the unique order id when no Stripe session exists. Retries and reprocessed orders produce the same client_id and the same transaction_id.

## Acceptance Criteria

- [x] Checkout session metadata carries the GA client_id and the analytics consent status at checkout time.
- [x] When creating the astrologer subscription checkout, subscribeAstrologer writes the GA client_id, the Firebase Auth uid (if signed in) and the analytics consent state into subscription_data.metadata, in addition to the checkout session metadata.
- [x] With consent = granted in the checkout metadata, the purchase event includes the real GA client_id from the metadata, user_id (= Firebase Auth uid) if signed in, transaction_id = Stripe session id, value, currency and items.
- [x] Without consent = granted in the checkout metadata, the purchase event is still sent, and its client_id is a one-way hash (e.g. SHA-256, truncated and formatted as a GA-style client_id) of the Stripe session id.
- [x] Subscription start, renewal and cancel events are sent for every successful corresponding Stripe event.
- [x] Renewal and cancel events read the client_id, uid and consent state from the Stripe subscription metadata, not from the current client state.
- [x] Renewal and cancel events include the stored real client_id and user_id only when the subscription metadata has consent = granted.
- [x] Renewal and cancel events whose subscription metadata lacks consent = granted are sent anonymously. Their pseudo client_id is a deterministic one-way hash of a Stripe identifier of that event. The exact identifier is still to be confirmed (proposed: the invoice id for renewal, the subscription id plus the cancel event id for cancel).
- [x] Withdrawing analytics consent after subscription checkout does not change the subscription metadata. Renewal and cancel events of that subscription keep following the consent state recorded at subscription checkout.
- [x] Without consent = granted, no user_id and no other identifier of the user is sent in any event.
- [x] No pseudo client_id can be reversed to its source Stripe identifier. Each comes only from a one-way hash and never equals the raw Stripe identifier.
- [x] Processing the same Stripe session or subscription event twice (webhook retry) produces an identical pseudo client_id and an identical transaction_id.
- [x] Webhook retries do not produce duplicate purchases (same transaction_id).
- [x] No birth data, names or emails appear in any event parameter.
- [x] The /privacy page (REQ-004) and the GA4 legal reasoning checklist state that anonymous server-side events carry a pseudonymous identifier derived from the transaction id, which can be linked to the payment record in Stripe/Firestore.
- [x] The /privacy page (REQ-004) states that analytics consent is recorded when the subscription starts and applies to later renewal and cancel events. It explains how to ask the operator (astroweb@mobilemindai.com) to stop attribution.
- [x] The GA4 legal reasoning checklist covers keeping the consent state in Stripe subscription metadata and applying it to later renewal and cancel events.
