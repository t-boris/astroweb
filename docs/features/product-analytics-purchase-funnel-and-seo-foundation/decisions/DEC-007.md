## Context

Per F-003, subscription renewal (invoice.paid) and cancel (customer.subscription.deleted) webhooks do not receive the checkout session metadata. REQ-002 requires these events to follow the same consent rules as purchase events (DEC-001, DEC-005), but there was no source for client_id and consent on renewal and cancel. The spec also did not say what happens if the user withdraws consent after subscribing.

## Alternatives

1. Copy client_id, uid and consent into subscription_data.metadata at checkout; renewals and cancels read them from the Stripe subscription; consent state at checkout applies for the subscription's lifetime
2. Send only subscription start with identifiers (if consented); always send renewals and cancels anonymously
3. Copy into subscription metadata as in option 1, plus a callable that updates consent on the active Stripe subscription whenever the user changes consent, so a withdrawal immediately anonymises later events

## Decision

When creating the astrologer subscription checkout, subscribeAstrologer writes the GA client_id, the Firebase Auth uid (if signed in) and the analytics consent state into subscription_data.metadata, in addition to the checkout session metadata. The webhook reads these values from the Stripe subscription metadata for renewal and cancel events. If that metadata has consent = granted, the event uses the stored real client_id and user_id. Otherwise the event is sent anonymously under DEC-005: no user_id or other user identifier, and a pseudo client_id that is a deterministic one-way hash of a Stripe identifier for that event. Later consent withdrawal does not update the subscription metadata: the consent state at subscription checkout applies to all of that subscription's events.

## Reason

This keeps channel attribution and retention/LTV by acquisition channel in GA4 at low implementation cost. Option 2 loses that attribution. Option 3 needs a new callable, sync with the banner, and handling for signed-out users whose subscription cannot be found. The team accepted that consent is fixed at checkout and that this is disclosed in the privacy page.

## Consequences

REQ-002 gets an acceptance criterion: subscribeAstrologer writes client_id, uid and consent into subscription_data.metadata, and renewal and cancel events are attributed only when that metadata has consent = granted. REQ-002's open note "per F-003" is resolved. AI inference, not yet decided: the default source for the anonymous pseudo client_id is the invoice id for renewals and the subscription id plus the cancel event id for cancels, so that retries are idempotent. This should be confirmed. REQ-004 (/privacy) must state that analytics consent is recorded when the subscription starts and applies to later renewal and cancel events, and explain how to ask the operator (astroweb@mobilemindai.com) to stop attribution. The GA4 legal reasoning checklist should cover this retention of consent state. Existing subscriptions created before this change have no such metadata and are treated as having no consent (anonymous).
