## Context

REQ-002 left an open assumption: which Stripe identifier seeds the pseudo client_id for renewal and cancel events. DEC-007 called the invoice id / subscription id + event id an AI inference to be confirmed. The webhook also receives invoice.payment_succeeded for the first invoice of a subscription, which the checkout.session.completed branch already covers. Confirmed by the owner on 2026-10-12 as part of plan approval.

## Alternatives

1. Use the invoice id for the first invoice too and drop the start event
2. Use the Stripe event id for renewals (changes on every redelivery of a different event for the same invoice)

## Decision

Pseudo client_id seeds (used only without consent = granted in the relevant metadata): purchase and subscription start = Stripe checkout session id; renewal = Stripe invoice id; cancel = '<subscription id>:<Stripe event id>'. The seed is hashed with SHA-256 and formatted as a GA-style client_id (two 10-digit numbers joined by a dot); it never equals the raw Stripe identifier and no user_id is sent. Renewal is recognised as invoice.payment_succeeded with billing_reason = subscription_cycle (the first invoice is covered by the start event). GA4 event names: star packs send the recommended 'purchase'; the astrologer subscription sends the custom events subscription_start (transaction_id = session id), subscription_renewal (transaction_id = invoice id) and subscription_cancel (transaction_id = event id), the first two with value and currency. Events are sent once, right after the corresponding Firestore effect succeeds; a redelivery that finds the work already done sends nothing.

## Reason

Each seed is a stable Stripe identifier of exactly that object, so retries of the same event produce the same client_id and transaction_id with no stored state. A separate renewal filter avoids counting the first invoice twice.

## Consequences

The open note in REQ-002 and DEC-007's 'AI inference, not yet decided' are resolved by this decision. GA4's built-in revenue metric counts only 'purchase', so subscription value is visible as an event parameter and in custom reports, not in standard revenue. The privacy page and the checklist name these identifiers.
